6. Probabilistic Data Structures — L4 Differentiator

These come up in deep dives and instantly signal senior-level thinking. Know when to use each and what error guarantees they provide.

Bloom Filter
URL deduplication in web crawlers, spam detection, cache pre-check
Hash the item into multiple bit positions. No false negatives (if it says absent, it's absent). Small false positive rate. Uses ~10 bits per element vs. 64-bit hash per element.
When: "How do you check if a URL has been crawled before at billions-of-URLs scale without RAM exploding?"
HyperLogLog
Approximate unique counts: DAU, unique IPs, unique searches
Estimates cardinality using the max number of leading zeros in hashed values. Uses only ~1.5 KB RAM regardless of set size. ~2% error rate.
When: "How does YouTube count 4B unique daily views without storing each viewer ID?" (Redis HLL natively)
Count-Min Sketch
Frequency estimation: Top K trending topics, heavy hitter detection
Hash item into d arrays of width w; increment all. On query, take the minimum across all arrays. Overcounts (never undercounts). Memory: O(d × w).
When: "How does Twitter find trending hashtags at 100K tweets/sec without storing all tweets?"
Trie (Prefix Tree)
Autocomplete / Typeahead, IP routing tables, spell checkers
Tree where each node is a character. All descendants of a node share a prefix. Store top-K completions at each node for O(prefix-length) lookup.
When: "Design Google's Search Autocomplete." Store in Redis (hot prefix cache) + Cassandra (full Trie persistence).

The 4-Step Interview Framework

Every system design interview at Google/Meta follows this structure. Internalize this so deeply that it becomes automatic under pressure.

1
Understand
Minutes 0–5 (+ Est. 0–10)
  • Ask clarifying questions before touching the whiteboard
  • Establish the read/write ratio — is this read-heavy (10:1) or write-heavy?
  • Define scale: How many DAUs? What's the target QPS?
  • Ask about latency requirements: real-time vs. eventual consistency?
  • Run the back-of-the-envelope estimation right here
2
Propose
Minutes 5–10
  • State the exact REST API endpoints: POST /api/v1/resource
  • Define the high-level database schema (table names, key columns)
  • State your technology choices with reasoning, not just names
  • Sketch the high-level architecture: Client → CDN → LB → API → DB
3
Deep Dive
Minutes 10–40
  • Identify the single biggest bottleneck in your design
  • For read-heavy: add caching layer (Redis), CDN for static assets
  • For write-heavy: async processing with Kafka, sharding strategy
  • Address the hard problem: concurrency, consistency, or geo-distribution
  • Draw the detailed data flow through each component
4
Wrap Up
Minutes 40–45
  • Summarize the key trade-offs you made (e.g., consistency vs. availability)
  • Mention what you would do differently at even larger scale
  • Proactively discuss failure modes: what happens when a node goes down?
  • Show the interviewer you think about operational concerns, not just theory
� L4 Signal vs. L3 Signal
L3: "I'll add a cache." L4: "I'll add Redis with LRU eviction, write-through policy, and probabilistic early expiration to prevent stampedes."
L3: "I'll shard the database." L4: "I'll shard by user_id using consistent hashing with 150 virtual nodes. Hot users get their own shard."
L3: Waits to be asked about failure modes. L4: Proactively says "If the cache node goes down, here's what happens..."
🔀 Fanout + Caching Strategy
Fanout-Write — Push to followers at write. Fast reads. Bad for celebrities (10M writes per post).
Fanout-Read — Merge on query. Slow reads. Use for high-follower accounts.
Hybrid — Write-fanout for normal users, read-fanout for celebrities. Instagram's actual approach.
Cache Eviction — LRU (most common), LFU (better for viral content), TTL-based.
🔒 Concurrency & Consistency
Pessimistic Lock — SELECT FOR UPDATE. Safe, slow. Use for ticket booking, financial debit.
Optimistic CC — Version check on write, retry on conflict. High throughput for low-contention.
Snapshot Isolation — Each txn sees a consistent snapshot. No dirty reads.
Eventual Consistency — Acceptable for likes/views counts. Never for balance or seat inventory.
📡 Real-Time + Streaming
Long Polling — Simple. Connection held open until data. ~1 req/sec per user overhead.
SSE — One-way push over HTTP/2. Lightweight. Use for notifications, live scores.
WebSocket — Full duplex. Required for chat. Scale by sticky sessions + pub/sub (Redis).
CDC (Debezium → Kafka) — Capture DB changes as events without polling. Use for cross-service sync.
🗺️ Geo + Multi-Region
Geohash — 2D → 1D string. Nearby points share prefix. Use for proximity search (Yelp, Uber).
Quadtree — In-memory tree, recursive grid splits. Better for dynamic density.
Active-Passive — One region serves traffic; failover to passive. Simple, higher RPO.
Active-Active — Both regions serve traffic. Requires conflict resolution. Use for Google Search, payments at Stripe.
� Technology Choice Cheat Sheet
Heavy writes, scale-out: Cassandra (LSM tree, no joins needed)
Strong ACID, relational: PostgreSQL / MySQL with read replicas
Text search, full-text: Elasticsearch (inverted index)
Time-series metrics: InfluxDB or Prometheus + Grafana
Graph queries: Neo4j or Amazon Neptune (social networks, fraud detection)
Object storage: S3 (never serve large files through API servers)

Week 1 — Infrastructure & Deployment

Goal: Understand how your code actually gets to production, how traffic enters the system, and how Node.js handles tens of thousands of concurrent requests.

⚙️ Jenkins & CI/CD Pipeline
  • Trace a pull request from merge to production — what are every stage in your Jenkinsfile?
  • Understand the difference between declarative vs scripted pipelines. Which does your team use?
  • Learn about blue/green and canary deployments — does your company do gradual rollouts?

  • Map the rollback procedure: what happens if a bad deploy goes live at 2am during a flash sale?
🔍 Investigate in your codebase Open your Jenkinsfile. Draw the pipeline stages end-to-end. Find where environment variables are injected (secrets management). Identify the production deploy trigger — is it automatic or gated?
🌐 Traffic Entry, Containers & Node.js at Scale
  • Container model: at a top ecom company, Node.js runs in Docker containers orchestrated by Kubernetes (K8s). Each container is single-process — horizontal scaling happens by adding more pods, not via the Node.js cluster module. The cluster module / PM2 clustering is relevant only if you're on bare VMs.
  • Event loop: Node.js is single-threaded with a non-blocking event loop. CPU-bound work (image processing, crypto, complex JSON transforms) blocks the loop and kills throughput — these should be offloaded to worker threads or separate services.
  • Graceful shutdown (SIGTERM): when K8s removes a pod it sends SIGTERM — your Node.js server must catch it, stop accepting new connections, drain in-flight requests, and close DB connections cleanly. Failure to do this causes request drops on every deploy.
  • Load balancer: understand your AWS ALB or Nginx setup — how it terminates SSL, routes to K8s service endpoints, and performs health checks (/healthz).
  • Traffic spikes: K8s HPA (Horizontal Pod Autoscaler) scales pods based on CPU/memory metrics. Understand your scaling policy's warmup time — a pod that starts cold can't serve traffic until it's warmed its caches and opened its DB connections.
🔍 Investigate in your codebase Find your Dockerfile and K8s deployment YAML. Check replicas, resource requests/limits, and livenessProbe / readinessProbe config. Search for SIGTERM handling in your Node server. Check your pg pool max config — multiplied by pod count, does total connections stay under Postgres max_connections?
✅ Questions you should be able to answer after Week 1
How long does a prod deploy take? What can go wrong at each stage?
If CPU spikes to 100% on a Node pod — what are the 3 most likely causes in your system?
What happens when your connection pool is exhausted during a traffic spike?

Week 2 — PostgreSQL Internals & CockroachDB

Goal: Understand exactly how your data is stored, queried, replicated, and kept consistent at scale. Know when each database is used and why.

🐘 PostgreSQL Deep Dive
  • MVCC (Multi-Version Concurrency Control): how Postgres allows concurrent reads/writes without locking by maintaining multiple row versions
  • WAL (Write-Ahead Log): every write goes to the WAL before the heap — this is how Postgres survives crashes and enables replication
  • VACUUM & autovacuum: dead tuples accumulate from MVCC — vacuum reclaims space. Understand why vacuum falling behind causes bloat and slowdowns
  • Query planner & EXPLAIN ANALYZE: learn to read query plans — Seq Scan vs Index Scan vs Bitmap Scan, why the planner sometimes ignores your index
  • Connection pooling (PgBouncer): Node.js can't open 500 raw Postgres connections — PgBouncer pools them. Understand transaction vs session pooling modes
  • Read replicas: how does your company offload analytics or heavy reads to replicas? What's the replication lag?
🔍 Investigate in your codebase Run EXPLAIN ANALYZE on your 3 most-called API queries. Look for Seq Scans on large tables. Check your pg_stat_activity for long-running queries. Find your most-bloated tables using pg_stat_user_tables.
🪳 CockroachDB — Why It Exists Alongside Postgres
  • CockroachDB's purpose: distributed SQL for horizontal write scale-out. Postgres maxes out on a single primary node — you can add read replicas but writes are bottlenecked. CockroachDB distributes writes across N nodes automatically.
  • Ranges & Raft: data is divided into ~128MB ranges. Each range is independently replicated via Raft to 3+ replicas. A write commits only when a majority (quorum) of replicas acknowledges it — this is what makes it fault-tolerant without a single point of failure.
  • HLC (Hybrid Logical Clocks): because nodes are geographically distributed, wall clocks drift. CockroachDB uses HLCs to assign causally-consistent timestamps to transactions without requiring a global lock — this is what enables serializable isolation at scale.
  • Postgres wire protocol: CockroachDB is Postgres-compatible at the protocol level — your Node.js services connect using the same pg driver. This is why the migration was feasible, but subtle SQL differences (e.g., sequences, certain JOINs) can surface as bugs.
  • Serializable isolation by default: unlike Postgres (default: Read Committed), CockroachDB defaults to Serializable — the highest isolation level. Cost: higher abort/retry rates under write contention. Your Node.js code must handle RETRY_WRITE_TOO_OLD errors.
  • Key decision: Cockroach for high-volume transactional data where writes scale horizontally (orders, inventory, cart), Postgres for relational complexity, analytics, and reporting where a single primary is sufficient.
🔍 Investigate in your codebase Find which services use which DB. Search for retry logic around CockroachDB transactions — if it's missing, you have a latent bug. Check if your ORM handles 40001 serialization errors. Look at your CockroachDB Admin UI: check range distribution, hotspot ranges, and replication factor.

Week 3 — RabbitMQ & Async Architecture

Goal: Understand every asynchronous flow in your system — what goes through RabbitMQ, why it's async instead of synchronous, and what happens when a consumer dies.

🐇 RabbitMQ Internals
  • AMQP concepts: producers publish to exchanges, not queues directly. Exchanges route to queues via bindings. Know all 4 types: Direct (exact routing key), Fanout (broadcast to all bound queues), Topic (wildcard — order.# matches any sub-key), Headers (match on message metadata).
  • Quorum queues (RabbitMQ 3.8+): classic mirrored queues are deprecated. Quorum queues use Raft to replicate messages to a majority of nodes before acknowledging — this is the correct HA setup for production. Classic queues can lose messages on broker failover.
  • Message persistence: durable: true queue + persistent: 2 delivery mode = messages survive broker restart. Without both, a RabbitMQ crash loses all queued messages. Note: persistence has a disk I/O cost.
  • ACK / NACK routing: nack(requeue=true) re-queues the message immediately (risk: infinite retry loop). nack(requeue=false) routes it to the Dead Letter Exchange → DLQ. Always use the latter with a retry count header to avoid poison message loops.
  • Dead Letter Queues (DLQ): silent production failures. A message that fails processing N times lands in DLQ. You need alerting on DLQ depth — a piling DLQ is usually the first sign of a downstream outage or a code regression.
  • Prefetch / QoS: channel.prefetch(N) limits unACKed in-flight messages per consumer. Without prefetch, one slow consumer can hoard all messages. Tune N to match your consumer's processing speed.
🔍 Investigate in your codebase Open the RabbitMQ Management UI. Check whether your queues are Quorum or Classic type. Find every NACK in your consumer code — does it use requeue: false? Check if you have a max retry count mechanism. Find DLQ bindings and verify they're monitored.
🔄 Async Flows in E-Commerce
  • Sync vs async boundary: payment auth and inventory reservation are synchronous (customer waits). Email confirmation, warehouse pick-list, analytics events, and loyalty points are async via RabbitMQ — the customer shouldn't wait for these.
  • Idempotency key pattern: payment webhooks are delivered at-least-once — Stripe can deliver the same payment_intent.succeeded event twice. Your handler must store the event ID in Postgres/Cockroach before processing, with a unique constraint — second delivery hits the constraint and returns 200 immediately without double-crediting.
  • Inventory consistency: product page shows eventually consistent count (cached, stale is OK). Checkout atomically decrements inventory in CockroachDB with a SELECT ... FOR UPDATE — if it hits 0, the order is rejected. Never trust the display count at checkout.
  • Saga pattern — compensating transactions: if Order Service succeeds but Inventory Service fails, you can't rollback the order in a distributed system. Instead, a compensating transaction runs: publish an order.cancelled event, refund the payment, restore inventory. This is the core of saga choreography.
  • RabbitMQ vs Kafka: RabbitMQ is a task queue — once a message is ACKed it's deleted. You cannot replay old messages. If you need event replay or audit trails (e.g., full order history), you need Kafka or a separate event store. Know which pattern your system uses and the implications.
🔍 Investigate in your codebase Find your payment webhook handler. Is there a processed_webhook_ids table or equivalent? Find your inventory decrement query — does it use a row lock? Search for compensating transaction logic. Find out if any RabbitMQ messages are critical enough to need replay — if yes, is there a separate event log?

Week 4 — React Frontend, APIs & Full-System Observability

Goal: Connect the frontend to every backend layer. Understand how a customer action propagates end-to-end, and how your team knows when something is broken before customers do.

⚛️ React at Ecom Scale
  • SSR vs CSR vs SSG per route: PDP (product detail page) needs SSR for SEO — Google must see the product content. Cart and user dashboard can be CSR since they're personalized and not indexed. Understand which rendering mode each route uses and why.
  • Core Web Vitals (CWV): Google's ranking signals measured in real user sessions — LCP (Largest Contentful Paint, target <2.5s), INP (Interaction to Next Paint, target <200ms), CLS (Cumulative Layout Shift, target <0.1). Your ecom revenue is directly affected by these scores.
  • Server-state vs client-state: UI state (modals, tabs) lives in React state. Server-state (cart contents, product data) should be managed by TanStack Query (React Query) — it handles caching, deduplication, background refetch, and stale-while-revalidate automatically. Not Redux.
  • Code splitting: React.lazy + Suspense splits the bundle per route. Critical path should only load the JS for the current page — pdp.bundle.js shouldn't load on the homepage. Check your Webpack or Vite chunk analysis.
  • Hydration mismatches: if your SSR-rendered HTML differs from what React expects on the client (e.g., server renders a timestamp, client renders a different one), React throws a hydration error and falls back to full CSR — defeating the SSR performance benefit entirely.
  • CDN strategy: static assets use Cache-Control: immutable, max-age=31536000 (content-addressed filenames). API responses use short TTLs (s-maxage=60) or no-store for personalized data. Understand which API routes your CDN is caching.
🔍 Investigate in your codebase Run a Lighthouse audit on your PDP and homepage. Check LCP, INP, CLS scores. Open Network tab and filter by JS — count bundles, find the largest. Check your bundle with webpack-bundle-analyzer. Find where TanStack Query or your data-fetching library is configured.
🔭 Observability — How You Know Things Are Broken
  • Structured logging (Pino/Winston): logs must be JSON — not plain strings. Every log line needs a correlationId (trace ID from the incoming request). This is how you find all logs for a single customer's failing checkout across 5 microservices in Datadog/Splunk.
  • Correlation ID propagation: the frontend generates a X-Correlation-ID header on every request. Node.js reads it, passes it to every downstream call (Postgres queries via log context, RabbitMQ message headers, outgoing HTTP). Without this, distributed debugging is nearly impossible.
  • 4 Golden Signals (Google SRE): Latency (p50/p95/p99), Traffic (RPS), Errors (rate %), Saturation (CPU/memory/DB connection pool %). P99 checkout latency crossing 500ms is usually your most important alert.
  • Distributed tracing (OpenTelemetry): auto-instruments Node.js, Postgres (via pg), RabbitMQ, and HTTP clients. Each operation becomes a span — you see the full waterfall for a single request. Essential for diagnosing which layer caused a latency spike.
  • RabbitMQ observability: three critical metrics: queue depth (growing = consumers behind), consumer count (dropped to 0 = consumer crashed), DLQ depth (growing = silent processing failures). Wire these to PagerDuty.
  • K8s + Node.js health: readinessProbe tells K8s when a pod is ready to receive traffic. livenessProbe restarts a hung pod. Understand what your probes check — a bad liveness probe causes thrashing restarts during DB connection issues.
🔍 Investigate in your codebase Search for X-Correlation-ID or x-request-id — is it propagated through all service calls? Find your OpenTelemetry or tracing SDK setup. Pick a recent slow API call in your tracing tool and identify which span accounts for the most time. Check if RabbitMQ metrics feed into your primary dashboard.
