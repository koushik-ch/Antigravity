1. Core Estimation Formulas

Round 86,400 seconds/day up to 100,000 to make mental math easier during the interview.

Queries Per Second (QPS)
QPS = (DAU × Avg Requests/User) ÷ 100,000
Peak QPS
Peak QPS = Average QPS × 2
Use ×3 or ×4 for spikey systems like live sports streaming.
Total Storage (5-Year)
Storage = Daily New Data × 365 × 5
Network Bandwidth
Bandwidth = Peak QPS × Avg Request Size

The 4-Step Interview Framework

Every system design interview at Google/Meta follows this structure. Internalize this so deeply that it becomes automatic under pressure.

1
Understand
Minutes 0–5 (+ Est. 0–10)
  • Ask clarifying questions before touching the whiteboard
  • Establish the read/write ratio — is this read-heavy (10:1) or write-heavy?
  • Define scale: How many DAUs? What's the target QPS?
  • Ask about latency requirements: real-time vs. eventual consistency?
  • Run the back-of-the-envelope estimation right here
2
Propose
Minutes 5–10
  • State the exact REST API endpoints: POST /api/v1/resource
  • Define the high-level database schema (table names, key columns)
  • State your technology choices with reasoning, not just names
  • Sketch the high-level architecture: Client → CDN → LB → API → DB
3
Deep Dive
Minutes 10–40
  • Identify the single biggest bottleneck in your design
  • For read-heavy: add caching layer (Redis), CDN for static assets
  • For write-heavy: async processing with Kafka, sharding strategy
  • Address the hard problem: concurrency, consistency, or geo-distribution
  • Draw the detailed data flow through each component
4
Wrap Up
Minutes 40–45
  • Summarize the key trade-offs you made (e.g., consistency vs. availability)
  • Mention what you would do differently at even larger scale
  • Proactively discuss failure modes: what happens when a node goes down?
  • Show the interviewer you think about operational concerns, not just theory
🔀 Fanout Strategies
Write — Push tweet to all followers at write time. Fast reads, slow writes. Best for accounts with few followers.
Read — Pull/merge feeds at query time. Slower reads, no write overhead. Best for celebrity accounts (millions of followers).
🔒 Concurrency Control
Pessimistic Lock — Lock the row before read. Safe, but slow under high contention.
Optimistic CC — No lock, check version on write; retry if conflict. High throughput.
Snapshot Isolation — Each transaction sees a consistent snapshot; no dirty reads.
📡 Real-Time Connections
Long Polling — Client holds connection open; server responds when new data. Simple.
SSE — Server pushes to client over HTTP. One-way, lightweight.
WebSocket — Full duplex. Required for chat/gaming. More complex to scale.
🗺️ Geo Distribution
Geohash — Maps 2D coordinates to a 1D string. Nearby points share a prefix. Good for range queries.
Quadtree — In-memory tree. Recursively splits map grids. Better for dynamic density.
